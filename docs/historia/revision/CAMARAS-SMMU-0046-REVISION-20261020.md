# Cámaras — parche SMMU 0046 (SID del IFE + ACTLR) para el frame RAW: diseño y revisión (20-oct-2026)

**Preparado, NO aplicado a ningún árbol, NO compilado en un kernel, NO flasheado.** Pedido del dueño: «prepara el parche SMMU de cámara para ouke6 (SID 0x200800, ACTLR 0x1, QTB) con su revisión, sin aplicarlo ni flashear». Fichero: `build/rootfs/deploy/camaras/patches/0046-uke-smmu-camera-ife.patch` (58 líneas; `patch -p1 --dry-run` OK contra `senemos-ouke5/linux-7.2.9`; compilado el objeto `arm-smmu-qcom.o` con la línea de compilación del propio kernel y los dos ficheros parcheados: **rc 0, sin avisos**).

## 1. Qué hay que resolver (medido)
Camss con `iommus` hacia `apps-smmu` (`qcom,sm7675-boot-smmu`) falla porque `qcom_uke_smmu_alloc_context_bank()` (`arm-smmu-qcom.c:816`) tiene una **lista blanca fija de SID** («outside Uke boot SMMU scope», `-EOPNOTSUPP`) y **rechaza todo SID que tenga ACTLR en `qcom,actlr`** del DT («boot stream needs an ACTLR override»). En el DT vivo `qcom,actlr` (31 entradas) trae: `0x800 mask 0x20 → 0x1` (IFE), `0x1860 → 0x1` (CDM), `0x18a0 → 0x103` (JPEG), `0x1820/0x1840/0x1880/0x18c0 → 0x1`, `0x18e0 → 0x103`. Además `uke-display-smmu.c: qcom_uke_display_init_context()` es el **único** `init_context` de la impl uke y solo escribe ACTLR para el dominio de display (`0x1c00/mask 2 → 1`): el camino genérico `qcom_smmu_set_actlr_dev/client_match` **no se usa** en esta impl.

## 2. El parche (2 ficheros, ~25 líneas útiles)
1. `uke-display-smmu.c`: `#define UKE_CAMERA_IFE_SID 0x200800` (= `0x800 | 0x20<<16`, igual que `0x801001` para el audio) y una función `qcom_uke_camera_init_context()` que, **solo si el dispositivo es `qcom,cliffs-camss`**, exige dominio S1, escribe `ACTLR = 1` (CMTLB, el valor OEM del IFE) en el banco de contexto recién creado (parado) y **comprueba la relectura** (`-EACCES` si no se retiene), igual que ya hace el display. `qcom_uke_display_init_context()` delega en ella para lo que no es display (USB/GPI siguen devolviendo 0 como antes).
2. `arm-smmu-qcom.c`: `sid == UKE_CAMERA_IFE_SID` en la lista blanca de la impl boot-smmu, y `continue` antes del bucle de rechazo por ACTLR **solo para ese SID** (su ACTLR ya se aplica en el paso 1).
3. Overlay `uke-cam-camss.dtso -DWITH_IOMMU`: `iommus = <&apps_smmu 0x800 0x20>` (**solo el IFE**; JPEG `0x18a0` con ACTLR `0x103` y CDM `0x1860` no se piden: no hacen falta para RDI en RAW, y evitan ampliar la lista blanca). Verificado con `fdtoverlay` + `check-cam.py`: OK.

## 3. Revisión: qué NO cambia y por qué es seguro
- **USB/GPI/audio/FastRPC/WLAN/display: ruta idéntica.** Las dos condiciones nuevas solo se cumplen con `sid == 0x200800` (lista) o `of_device_is_compatible(dev, "qcom,cliffs-camss")` (ACTLR); ningún otro dispositivo las cumple. Sin overlay de camss el kernel se comporta como ouke5.
- **Sin overlay, el kernel no toca la cámara:** el nodo `camss` no existe hasta cargar `uke_cam_camss.ko` (como hoy).
- **ACTLR escrito en un contexto nuevo y parado, con relectura obligatoria**, el mismo patrón que el display (ya validado en el panel).
- **No toca** `qcom_smmu_alloc_context_bank` genérico, ni TBU/QTB, ni la política de bypass.

## 4. Riesgos que el parche NO elimina (honestos)
| # | Riesgo | Mitigación / prueba |
|---|---|---|
| S1 | **QTB de cámara** `cam_hf_qtb@14d2000` (`qcom,qtb500`, streams 0x800–0xbff, `interconnects` a `interconnect@1400000` nodo 0xb): el kernel uke **no gestiona TBU/QTB** (solo USB `anoc_2_qtb` y LPASS, que están en dominios siempre activos). Si el TBU de cámara necesita voto de NoC/energía para traducir, el VFE se quedará esperando sin fault (timeout de frame) | probar con **un solo frame, `--stream-count=1`, timeout**; si no llega, el siguiente paso es el voto ICC `mmnoc 0xb` del DT OEM (otro parche, M) |
| S2 | **Sin ICC de CAMNOC** (la capa cliffs de senemos es USB/display): ancho de banda sin votar | primer frame en el modo **2104×1560** del sensor (≈ ¼ del ancho de banda), después 4208×3120 |
| S3 | Un SID/ACTLR mal ⇒ `Unhandled context fault` (el riesgo ya conocido de docs/historia/AGENTS.md) | el parche solo admite 1 SID y verifica el ACTLR; prueba corta; **sin instrumentar el SMMU en runtime** |
| S4 | `mask 0x20` hace que el SMR cubra también el SID `0x820`/`0x800|0x20` (IFE0/1/2): posibles solapes con otros SMR | `check` en el log: un único grupo IOMMU para `acb6000.isp`; no hay otro dispositivo con esos SID |
| S5 | Rieles/relojes de cámara de GCC (`camera_hf_axi`) | ya cargados por camss; el `ungate` de C4 cubre ahb/xo |

## 5. Cómo construir ouke6 sin recompilar los módulos de todo el mundo (propuesta)
Un cambio de **cuerpo** en `arm-smmu-qcom.c` no altera ningún símbolo exportado ni estructura: `CONFIG_MODVERSIONS` está **desactivado** en ouke5 (la columna CRC de `Module.symvers` es `0x00000000`): no hay comprobación de CRC al cargar, solo la cadena vermagic. Se puede construir el kernel con **el mismo `LOCALVERSION -ouke5`** (release idéntica, `KBUILD_BUILD_VERSION=6` para distinguir el banner/`#6`) y **reutilizar los `.ko` de audio, BT y cámara ya instalados** (vermagic igual). Gate previo obligatorio (hecho, ver §8): el conjunto `(tipo,nombre)` de `System.map` y los `__ksymtab_` del build nuevo = **idénticos** a los de ouke5. Pasos (no ejecutados): `rsync` del árbol ouke5 → copia, `patch -p1 < 0046…`, build desde cero en un `O=` nuevo (≈ 55 min), repack `repack-senemos-v5.py` derivado a `v6`, fila de ledger con el sha del boot v6 y `flash-senemos-v5-gated.sh` (derivado) con `--rollback v5` (= boot v5 `f3d3bc82…`, mismo `/lib/modules`). El `--pre` no haría falta (módulos ya instalados). Si el gate de `Module.symvers` falla, se vuelve al plan de release nueva (`ouke6`) con recompilación de módulos.

## 6. Plan de prueba C5b (tras el flash, con orden del dueño)
Precondiciones: **batería ≥ 30 % con cargador de pared** (hoy 1 %: se reinicia y se suspende en bucle), un único lector ACM, `dmesg -w` a fichero, `systemd-inhibit`, tablet recién arrancada (overlays limpios; si no, reiniciar). Secuencia: camcc (`ungate=1`) → `uke_cam_rear` + `i2c-qcom-cci` (con `driver_override` y `simple-pm-bus` desenganchado) → `uke_ov13b10` → `uke_cam_camss` (build `-DWITH_IOMMU`) + `uke-camss` → `media-ctl` (`csiphy1→csid0→vfe0_rdi0`, modo 2104×1560) → `v4l2-ctl -d /dev/video0 --stream-mmap --stream-count=1 --stream-to=f.raw` con timeout. **Aborta** si: aparece `Unhandled context fault`/`stream fault`, `ACTLR write did not stick`, un oops, o no hay frame en 10 s. Techo: 3 ciclos por hipótesis.

## 7. Decisión pendiente del dueño
