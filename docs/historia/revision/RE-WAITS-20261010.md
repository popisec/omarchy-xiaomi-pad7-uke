Solo-PC (10-oct-2026). Tablet no tocada, sin builds, sin repack, sin ledger.
Base nuestra: `build/kernel-pokes/k52-L15-tree/drivers/gpu/drm/msm/adreno/a6xx_gmu.c`

## 1. Tabla exhaustiva: cada espera/delay/poll vendor afirmar→liberar y su par nuestro

Orden del path vendor (`a6xx_gmu_boot`: clks → rscc_wake → load_fw → register_config
→ irq_enable → device_start). Unidades: `readl_poll_timeout` = (intervalo_us,
timeout_us); `gmu_core_timed_poll_check(dev,reg,exp,timeout,mask)` con timeout en
**ms** — inferido, no leído (el núcleo kgsl cerrado no está en el clone sparse):
`gen7_timed_poll_check_rscc` hace `readl_poll_timeout(...,100,timeout*1000)` y se la
llama con `100`; `timed_poll_check_rscc` (a6xx) reenvía el MISMO valor a ambas ramas
(`gmu_core_timed_poll_check` y `readl_poll_timeout(*1000)`), luego las unidades tienen
que coincidir o las dos ramas se comportarían distinto. `GPU_START_TIMEOUT` =
`GMU_START_TIMEOUT` = `100 /* ms */` (`adreno_a6xx_gmu.c:525-526`).

ningún `udelay`, ningún `usleep_range`, ningún `dsb`. Sus únicas sincronizaciones son
`wmb` + polls de 100 ms. No hay espera oculta que copiar salvo las filas 1-3/9-10.

## 2. Cuestión (b): ¿falta una espera entre S1 y el release? — NO (vía muerta)

El vendor **ni siquiera tiene S1 en el path boot**: `a6xx_gmu_boot` no afirma el reset
nunca (el CM3 sale del power-on del GDSC; `register_config` programa CFG una vez y
`device_start` libera). Su separación CFG→release son ~10 writes MMIO sin un solo
delay. Nuestra separación S1 (`:683`) → release (`:804`) contiene: 1 read + 1 write
(gen9), ~12 reads K44 con 5 `pr_flush`, writes+reads GBIF, 6 writes L10-recfg, pokes y
`pr_err` por consola — **órdenes de magnitud MÁS tiempo** que el vendor (cada flush a
consola serie son ms). Si el CM3 necesitara "asentarse" tras S1, ya lo tiene de sobra.
Añadir un `udelay/msleep` explícito sería DIVERGIR del vendor, no converger. Y la
config que el vendor programa "justo antes de liberar" ya la reprogramamos tras S1
(L10 + L13s para GENERAL_10/8, informe RE-STUB-20261010). **Nada que diseñar aquí.**

## 3. Cuestión (c): ¿falta `udelay` tras el release o basta `wmb`? — basta `wmb` (vía muerta)

Vendor: `SYSRESET=0; wmb(); poll-inmediato`. Nosotros: idéntico (`:804-805` + poll
`:832`). El poll con intervalo 100 us ES la espera (100 ms de techo, valor L11
vendor-exacto). Un `udelay` extra antes del poll solo retrasaría la primera lectura
sin cambiar el techo ni la condición; el vendor demuestra que no hace falta. El `dsb`
no aparece en ningún lado del path vendor (solo `wmb`/`smp_rmb` en paths NMI ajenos).
**Nada que diseñar aquí.**

## 4. Cuestión (a): RSCC-wake — delta real, pero latente (no explica #575)

Filas 1-3: nuestro `a6xx_rpmh_start` espera **10 ms** donde el vendor espera **100 ms**,
y omite el `wmb` tras `REQ=BIT(1)`. Es una divergencia 10x probada línea a línea, en
la negociación exacta que se nos pidió revisar. PERO la firma del fallo actual es
`S4-pollFAIL` (CM3 suelto, INIT_RESULT sin bit 8) con `H6-rsc` superado: el RSCC
despierta siempre en la práctica, luego este delta **no es el asesino del CM3**.
Corregirlo no debería mover la aguja del CM3; lo que compra es: (i) alinear con vendor
una vía que hoy es 10x más impaciente, (ii) inmunidad ante arranques lentos (warm boot
tras GDSC-off, primer boot frío con rails fríos) donde 10 ms pueden expirar de forma
intermitente, (iii) extender la misma alineación a los polls hermanos (HFI, sleep)
que comparten el timeout corto heredado de mainline. Riesgo: nulo — solo alarga el
techo del peor caso; el camino rápido no cambia.

## 5. Fix candidato L16 (base L15, solo-MMIO + techos, cero structs/RAM/SMMU)

Tres micro-hunks en `drivers/gpu/drm/msm/adreno/a6xx_gmu.c`, estilo C2:

```c
/* UKE-L16 (RE-WAITS-20261010 fila 1-3): RSCC-wake vendor-exacto.
 * El vendor hace REQ=BIT(1) + wmb() + poll ACK 100ms + poll SEQ_BUSY 100ms
 * (GPU_START_TIMEOUT). Nosotros: sin wmb y 10ms (10000us). */
gmu_write(gmu, REG_A6XX_GMU_RSCC_CONTROL_REQ, BIT(1));
wmb();  /* <-- añadir */
ret = gmu_poll_timeout(gmu, REG_A6XX_GMU_RSCC_CONTROL_ACK, val,
    val & (1 << 1), 100, 100000);   /* 10000 -> 100000 */
...
ret = gmu_poll_timeout_rscc(gmu, REG_A6XX_RSCC_SEQ_BUSY_DRV0, val,
    !val, 100, 100000);             /* 10000 -> 100000 */
```

## 6. Notas de honestidad

- La unidad ms de `gmu_core_timed_poll_check` es **inferencia** (§1, doble rama de
  `timed_poll_check_rscc`): el núcleo kgsl cerrado no está en el clone y no se pudo
  leer la definición. Si fuese distinta de ms, las filas 2-3/9-10 caerían — pero
  entonces el propio vendor sería incoherente entre sus dos ramas RSCC, así que se
  considera sólida.
- `fw_load` sin `wmb` final (fila 4): el `gmu_read(CORE_FW_VERSION)` + pokes que
  siguen ordenan igual; no se incluye en L16 para mantener el diff mínimo. Mencionado
  por completitud, no como delta.
- No se propone ningún `udelay/msleep` nuevo: sería inventar una espera que el vendor
  no tiene.
