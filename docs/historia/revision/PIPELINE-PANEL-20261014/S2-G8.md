## 2. Estado real del asunto (evidencia)

### 2a. Vendor, reset de host_init (`ctrl_reset`, pasos 8/10 del prepare, ANTES de rails)

`dsi_ctrl_hw_cmn_ctrl_reset.c:16-27` (offsets `.ko`/CAF = mainline +4):

```c
uVar1 = readl_relaxed(*param_1 + 4);          /* CTRL */
writel_relaxed(uVar1 & 0xfffffffd, ...+4);    /* limpia BIT1 = VID_MODE_EN */
writel_relaxed(uVar1 & 0xfffffffc, ...+4);    /* limpia BIT1+BIT0 = VID + ENABLE */
writel_relaxed(0x100a00, ...+0x11c);          /* CLK_CTRL: force clocks reducido */
writel_relaxed(1, ...+0x118);                 /* RESET=1 */
DataSynchronizationBarrier(...);
writel_relaxed(0, ...+0x118);                 /* RESET=0 — SIN sleep entre medias */
DataSynchronizationBarrier(...);
writel_relaxed(0, ...+0x11c);                 /* CLK_CTRL=0 */
writel_relaxed(uVar1 & 0xfffffffd, ...+4);    /* restaura CTRL con VIDEO APAGADO */
```

Pulso ≈ 2 writes + 1 DSB (≈ decenas de ns). Llamado desde `dsi_ctrl_host_init.c:86`
(vía slot ops `0x1b0`, registrado en `dsi_catalog_cmn_init.c:38`), invocado en
`dsi_display_prepare.c:195-198` para ambos ctrls **antes** de `pre_prepare` (rails+reset-GPIO).

### 2b. Vendor, reset del prepare (`soft_reset`, paso 13: tras LINK_CLK, antes de panel_prepare/DCS)

`dsi_ctrl_hw_cmn_soft_reset.c:12-25`:

```c
CTRL &= ~7;                    /* apaga EN+VID+CMD (línea 13) */
CLK_CTRL |= 0x200b3f;          /* force clocks completo (línea 16) */
RESET = 1; dsb;
func_0x00387218(0x10c7);       /* <-- el pulso (línea 20) */
RESET = 0; dsb;
CLK_CTRL = guardado;           /* restaura clocks */
CTRL = guardado íntegro;       /* restaura CTRL completo (línea 25) */
```

### 2c. El pulso vendor es `udelay(1)` — probado a nivel de instrucción, no "de memoria"

Disasm propio del `.ko` (`llvm-objdump --arch-name=aarch64 -d
--disassemble-symbols=dsi_ctrl_hw_cmn_soft_reset`, función en file-offset `0x12d430`):

```
12d498: mov  w0, #0x1        → RESET=1 (write a base+0x118)
12d4a8: dsb st
12d4ac: mov  w0, #0x10c7      // =4295
12d4b0: bl   ...              → reubicación R_AARCH64_CALL26 a __const_udelay
12d4b8: mov  w0, wzr          → RESET=0
```

Reubicación verificada en `/tmp/opencode/msm.reloc` (97127 entradas):
`000000000012d4b0 … R_AARCH64_CALL26 … __const_udelay + 0`.
Y el propio árbol vivo lo cierra: `arch/arm64/lib/delay.c:76` define
`udelay(n) → __const_udelay(n * 0x10C7UL)` ("2**32/1000000 rounded up").
Luego `__const_udelay(0x10C7)` **es** `udelay(1)` = **1 µs**. El "1 µs" de G8 queda
demostrado, no citado.

### 2d. Vendor, granularidad del enable (el "orden" de G8)

- `dsi_ctrl_hw_cmn_ctrl_en.c:10-16`: force `CLK|=0x200B3F`; `CTRL = (CTRL&~1)|(en&1)`
  (**solo BIT0 ENABLE**; VID no se toca); restaura CLK. Tres escrituras separadas.
- `dsi_display_vid_engine_enable.c:25`: `set_vid_engine_state(...,1)` → BIT1 VID_MODE_EN
  **después** de los 108 DCS (SECUENCIA §A pasos 18→20).
- Orden vendor completo en el enable: host_init(sin ENABLE) → rails+reset-GPIO →
  LINK_CLK → ENABLE → soft_reset(1 µs) → 2º reset-GPIO → 108 DCS (motor de vídeo OFF) →
  VID_MODE_EN.

### 2e. Mainline vivo (lo que hay que cambiar y lo que no)

| # | Vendor | Mainline vivo (`k52-L16-tree`) | ¿Vivo en el path del fallo? |
|---|---|---|---|
| 1 | Pulso reset prepare = 1 µs (udelay) | `dsi_sw_reset` :1147-1149: RESET 1 → **`msleep(20)`** → RESET 0 (×20.000) | **SÍ**: `power_on` = timing → sw_reset → ctrl_enable, en cada arranque |
| 2 | `ctrl_reset` restaura CTRL **sin VID** | `dsi_sw_reset` :1152-1154 restaura CTRL **íntegro** (re-arme VID) | NO en primer arranque (CTRL parte de 0: disable y restore son no-ops). Solo re-modeset/disable = H5-5a, otra variable |
| 3 | ENABLE en write propio; VID el último, tras DCS | :919-921 `CLK_EN\|carriles\|ENABLE` juntos en `power_on`; :1221+1226 `VID\|ENABLE` juntos en `host_enable` **antes** de los DCS | Estructural: repartido en `dsi_ctrl_enable` + `dsi_op_mode_config`, más orden panel-vs-host |
| 4 | Rails+reset-GPIO con PHY en LP11 y host iniciado; DCS con host ENABLE y vídeo OFF | Panel `o82_prepare` (:325-389) hace rails→reset→**DCS completos** con `prepare_prev_first=true` (:726), es decir **antes** del `pre_enable` del host; cada DCS además bloquea en VIDEO_DONE (:1215-1234) | Estructural DRM (solapa con S3: orden del prepare, y S4: vídeo-antes-de-DCS) |

Conclusión honesta: la evidencia alcanza para el cambio exacto del **pulso** (fila 1:
una variable, viva en el path del fallo, diff abajo). Las filas 2–4 quedan derivadas pero
**fuera** de este diff: la 2 es no-op en primer arranque (ciclo H5-5a de S4 si el pulso no
mueve nada); las 3–4 exigen reordenar el secuenciado DRM/host/panel y solapan con S3/S4 —
no son "un cambio", y apilarlas aquí violaría un-cambio-por-ciclo (E1).

## 5. Riesgos y refutaciones que aplican (REFUTADO/LECCIONES)

- **No colisiona** con `REFUTADO.md`/`LECCIONES.md` (~56 refutaciones revisadas por grep:
  ninguna menciona `sw_reset`/`soft_reset`/`CTRL_ENABLE`/pulso del host; lo más cercano es
  doctrina de no instrumentar SMMU en runtime — irrelevante aquí).
- Riesgo bajo-medio (GAPLIST lo tasa "medio: toca el orden", pero este diff **no** toca el
  orden, solo la duración del pulso; el reset sigue con clocks forzados y barreras `wmb`
  intactas). El vendor demuestra que 1 µs basta en los 3 paths equivalentes.
- Riesgo de interpretación: un `msleep(20)` también duerme al thread 20 ms en mitad del
  `power_on`; con `udelay(1)` el `power_on` llega ~20 ms antes al `ctrl_enable`. Si la firma
  se mueve, hay que atribuir al pulso, no al desplazamiento temporal (el desplazamiento es
  inseparable del cambio; se declara aquí para no re-descubrirlo).
- L36 (ex-`k52L33-tree`, flush retirado por mover la muerte *antes*) no aplica: este diff no
  toca timing/flush/VIDEO_DONE; si la muerte se adelantara igual, sería evidencia nueva,
  no repetición de L36.
- Presupuesto: 1 escritura boot. Si el gate del día no da (≤2/día, retries, batería), este
  peldaño espera — no se apila con ningún otro diff del pipeline (regla: un cambio por ciclo).

## 6. Qué NO hacer / lo que queda fuera

1. **No** cambiar el restore a `ctrl & ~VID_MODE_EN` en este ciclo (fila 2 del §2e): es H5-5a
   (S4), no-op en primer arranque, segunda variable. Solo si el pulso no mueve nada.
2. **No** cambiar el force `DSI_CLK_CTRL_ENABLE_CLKS` a `0x100A00`/`0x200B3F` (H5-5b, S4):
   bits 20/11/9 son `DYNAMIC_FORCE_ON` v2.8; documentado, no tocado.
3. **No** reordenar ENABLE/VID/DCS (filas 3–4): propiedad de S3 (dónde corre el prepare,
   `prepare_prev_first`) + S4 (vídeo-antes-de-DCS y espera por comando). Requiere rediseño
   del secuenciado, no un diff de una variable.
4. **No** re-probar G4/G5/G6/G7 (refutados/inertes) ni usar G1 como diagnóstico.
5. **No** renombrar a "refutado" un posible fallo de este peldaño sin el control: el veredicto
   exige misma tablet, mismo dtbo/modo, predicción pre-registrada y doble captura (doctrina
   G4/G7, lo mejor del día según la auditoría §5.1).
